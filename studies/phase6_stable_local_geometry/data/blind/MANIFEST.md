Fresh label instrument built after `p0/P0_GRADING_BRIEF_AUDIT.md`. The
previous round showed raters the system's own tags (depth, role,
in-statement, kind) and encoded two of its predictions in the rubric.
Nothing a rater reads in this round contains any system coordinate.

### Target eligibility

1. non-generated (`gen` flag false), kind 0 or 1, depth >= 11;
2. >= 3 incidences;
3. sampling-only aux-name filter from `src/pilot_sample.py`
   (`casesOn`/`rec`/`_aux`/`macroRules`/`_unexpand`/leading `_` ...);
4. module under `Mathlib.`, not under `Mathlib.Tactic`;
5. statement AND body located **exactly** in the Mathlib source.

Criterion 5 is new and it is a real restriction, recorded here rather
than hidden: it drops Mathlib's machine-generated lemmas (`@[simps]`,
`@[reassoc]`, unnamed `@[to_additive]`/`@[to_dual]`) from the target
frame, because those declarations have no source text to show and no
human proof to judge. It skews the target sample away from category
theory `_hom_app`/`_obj` projection lemmas and away from the additive
halves of algebraic hierarchies. It is applied to targets only.

### Candidate universe (unfiltered)

Per target, ALL of its incidence declarations that are load-bearing
(roles 0/1/2/7 = applied / let-value / explicit-arg / unresolved) PLUS
all definition-kind declarations cited in any role — i.e. the U1D pool
of `mathmap_eval/corpus.py`, verbatim. Generated candidates are
redirected to their nearest non-generated dot-prefix owner and dropped
if that owner is the target itself; then deduplicated. Targets with
fewer than 3 or more than 25 candidates were resampled.

**No inclusion policy, ranking, lane or score touches this pool.** The
labels are meant to judge the pool, so the pool must not have been
pre-judged.

- candidate slots: 1,708, mean 14.2 per target,
  min 4, max 25.

## Statement extraction

Statements come from the Lean source: `all_modules.tsv` gives the
module, `src/lean_source.py` indexes that file by fully qualified name
(namespace stack + declared name), including structure/class fields,
inductive constructors, `extends` parent projections, `mk`
constructors, explicitly named `@[to_dual X]` / `@[to_additive X]`
targets, and anonymous `instance : C ...` blocks matched by Lean's
`inst<C>...` naming. Mathlib source is `corpusenv/mathlib`; `Init.*`,
`Lean.*`, `Std.*` come from the v4.33.0 toolchain source; the rest
from `.lake/packages`.

- targets: 120/120 statements and bodies located
  exactly (enforced by eligibility criterion 5, above).
- candidates: 1,659/1,708 located = **97.1%**; **2.9% could not be located** (49 of 1708).
- of those located, 1,654 are the declaration's own
  source text and 5 are approximate: the
  declaration is generated by Mathlib and the brief shows the
  declaration it was generated from, prefixed with a one-line comment
  saying so. Those are flagged as `translated` / `generated-from` in
  `keymap.json`.
- a candidate whose source could not be located is rendered as its
  declaration name alone (flagged `not-found` in `keymap.json`).

Match kinds: `{"exact": 1551, "anon-instance": 86, "MISS": 49, "lastcomp": 15, "suffix": 2, "translated": 5}`

Known residual signal, stated so it can be controlled for: a
`not-found` candidate is visibly different from the others (a bare
name, no statement), and it correlates weakly with being
machine-generated — the previous round treated the generated flag as
hidden. This affects 49 of 1708 candidate slots (2.9%). Exclude those slots in any
analysis where it matters; `keymap.json` marks every one of them.

## Blind-contract checklist

Every rendered batch in `batches/` was grepped, case-insensitively,
for the vocabulary that contaminated the last round. Occurrences
inside a ```lean fence are Lean source text (Mathlib really does have
declarations named `Nat.rec`, fields named `map`, and the `instance`
keyword); occurrences OUTSIDE the fences would be instrument leakage.
The contract is that the outside-source count is zero.

| term | occurrences in batch files | outside Lean source |
|---|---|---|
| `depth` | 0 | **0** |
| `role` | 0 | **0** |
| `in-statement` | 0 | **0** |
| `instance-slot` | 0 | **0** |
| `lane` | 0 | **0** |
| `rank` | 0 | **0** |
| `score` | 0 | **0** |
| `kind` | 0 | **0** |


**Contract holds: YES.**

What a rater sees, exhaustively: the batch header, the rubric text
above verbatim, the output-format example, and per item — the target's
statement source, its proof/construction source, and a numbered list
of candidate names each with its statement source. Nothing else.

What a rater never sees: depth or depth band, role or role name,
in-statement vs introduced-by-proof, declaration kind, lane, rank,
score, rarity, in-degree, generated flag, inclusion policy, or any
hint about how many grades of each value to expect. The rubric names
no constant, no typeclass, no tactic, and no expected distribution.

The rubric, identical in all 12 batches:

```
Grade each candidate 0-4 by its mathematical function in THIS proof/construction:
4 = a core move: the proof's central idea or decisive step depends on it
3 = a major step: substantive mathematics the proof genuinely builds on
2 = a legitimate connective step: honest but routine glue between the real steps
1 = boilerplate: bookkeeping that any formalization would need; contributes no mathematical content
0 = noise: irrelevant or purely administrative
Judge from the mathematics alone. If unsure between two grades, give the lower.
There are no quotas; a proof may have several 4s or none.
```
