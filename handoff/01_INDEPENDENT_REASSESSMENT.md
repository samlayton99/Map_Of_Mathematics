# Independent Reassessment of the v4 Direction

## Verdict

The clarified intuition is strong, but the prior v4 handoff overcommitted to it as an architecture.

The problem was not length. The problem was epistemic status.

The package contained a conviction register, but the master prompt still froze several untested choices:

- named declarations as *the* primary map nodes;
- selective branch-specific expansion as *the* deterministic map operation;
- theorem interface, certificate support, and exact proof as a settled three-level hierarchy;
- statement families, proof artifacts, application occurrences, certificate routes, use events, annotations, and views as a target schema;
- a declaration-centered AND–OR hypergraph as the object to build.

These are coherent design proposals. They are not yet empirical conclusions.

## Where the prior reasoning was too accommodating

The conversation repeatedly produced a clearer conceptual formulation. Each clarification was valuable. But conceptual coherence gradually acquired the emotional force of evidence.

The assistant was too willing to respond to the latest framing with phrases such as “this is the correct center” and then translate it into frozen implementation instructions.

That is a form of confirmation bias even when every individual statement is plausible.

## What does not smell off

The following remains well grounded:

1. Lean already provides a trustworthy exact formal substrate.
2. Gates 0–1 produced a narrow, useful serialization and identity layer.
3. Named declarations are important human-chosen abstraction boundaries.
4. Type/interface references and body/proof references answer different questions.
5. Local context and goal matter for learning declaration relevance.
6. Formal and semantic data must remain separate.
7. A future natural-language tagging harness can attach valuable metadata without changing formal truth.

## What smells off

### 1. Ontology before measurement

The prior package specified the objects before determining which views correspond to useful mathematical units.

### 2. Support mistaken for explanation

A proof-term support set is exact as a record of constants occurring in one certificate. It may be a poor proof hint because it can contain:

- typeclass infrastructure;
- coercions;
- low-level recursors;
- automation artifacts;
- declarations used only in types;
- repeated or incidental constants;
- no ordering or local role information.

Calling it an AND hyperedge risks implying joint logical necessity that has not been established.

### 3. Human-scale route assumed recoverable

Lean proof terms preserve formal construction, not necessarily the author's conceptual decomposition. Tactic traces preserve source-level actions, but automation and elaboration can obscure attribution. The useful middle layer may require natural-language or human tagging rather than pure extraction.

### 4. Selective zoom assumed useful

Exact declaration expansion is easy to define. Whether it is the right zoom for humans or agents is a product and scientific hypothesis. More formal detail may not resolve conceptual confusion.

### 5. Success criteria biased toward construction

“Build a coherent map” can succeed whenever the schema is internally consistent. That is not the same as showing the map captures useful mathematical structure.

### 6. Too many future concepts entered the current schema

Alternative proofs, semantic annotations, theorem families, use events, and multiple route levels were all represented before their necessity was demonstrated.

## Corrected posture

The project should now ask:

> Which representation of a Lean proof best approximates the reusable named mathematical structure that humans and agents need for navigation?

The answer may be:

- direct support;
- filtered support;
- application occurrences;
- source tactic events;
- text plus structure;
- natural-language annotations;
- or a hybrid.

The next phase should compare these rather than assume one.
